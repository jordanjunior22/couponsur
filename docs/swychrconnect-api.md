# Direct API (swychrconnect / AccountPe)

Source: docs pasted by the user. The API host in the docs is `api.accountpe.com`.

Direct API collects funds from customers via mobile money or digital cash. You control the UI, the flow, and when to trigger the payment (no hosted page or redirect). It supports 18 African countries; available payment methods differ per country.

## Authentication

Either credential works:

- **Bearer token**: JWT from login. Header `Authorization: Bearer <token>`. For authenticated-session calls.
- **API key**: long-lived, for server-to-server. Header `Api-Key: <your_api_key>`. Generate or view it under Payment Gateway -> API Key.

If the account has an IP whitelist, requests must come from a whitelisted IP regardless of credential.

Keep the real API key in an env var (e.g. `.env.local`), never in this file or in code.

## Create payment request

`POST https://api.accountpe.com/api/payin/create_payment_request`

| Field | Type | Required | Description |
|---|---|---|---|
| country_code | string | Yes | Two-letter ISO country code of the customer, e.g. `"CM"` |
| name | string | Yes | Full name of the customer |
| transaction_id | string | Yes | Unique reference generated by you. Must be unique across your account; reuse returns 400 |
| amount | number | Yes | Amount to collect, > 0 |
| email | string | No | Customer email |
| mobile | string | No | Customer mobile, matching the format for the chosen payment method |
| payment_method | string | No | From the payout_methods endpoint (e.g. `"MTN"`, `"ORANGE"`) |
| description | string | No | Human-readable description |
| pass_digital_charge | boolean | No | If true, adds a 2.5% digital charge on top of `amount` (customer pays the fee) |
| om_otp | string | No | Orange Money OTP. **Required** when `payment_method` is `"ORANGE"` and `country_code` is `"CI"`, `"SN"`, or `"BF"`. Otherwise 400: `"om_otp is required for network=ORANGE payins in CI/SN/BF"`. Collect the OTP the customer receives on their Orange Money line before calling |
| reason | string | No | Reason/purpose passed to the underlying gateway |
| callback_url | string | No | Webhook called when payment succeeds |
| failed_callback_url | string | No | Webhook called when payment fails |
| source | string | No | Free-form source tag; defaults to `"API"` |

### Example request

```bash
curl -X POST https://api.accountpe.com/api/payin/create_payment_request \
  -H "Api-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "country_code": "CM",
    "name": "Jane Doe",
    "email": "jane@example.com",
    "mobile": "651791902",
    "transaction_id": "TXN-20260805-0001",
    "amount": 5000,
    "payment_method": "MTN",
    "description": "Order #1042",
    "pass_digital_charge": true,
    "callback_url": "https://yourapp.com/webhooks/payment-status",
    "failed_callback_url": "https://yourapp.com/webhooks/payment-failed"
  }'
```

### Success (200)

```json
  "data": {
    "id": 10234,
    "transaction_id": "TXN-20260805-0001",

```

## Customer journey

1. **Check available payment methods**: call `/api/payout/payout_methods` for the customer's country to know which methods and mobile formats to show.
2. **Collect customer details**: name, email, mobile, chosen payment method, in your own checkout UI.
3. **Call Direct API**: `POST /api/payin/create_payment_request` with a unique `transaction_id` per order.
4. **Show a pending state**: collections are typically asynchronous; the customer confirms on their phone/wallet.
5. **Get notified**: provide `callback_url` (success) and `failed_callback_url` (failure) to receive webhooks, then update order state.

## Admin auth: get a bearer token

Body:

| Field | Type | Required |
|---|---|---|
| email | string (email) | Yes |
| password | string | Yes |

Responses:

## Create a payment link

Creates a hosted payment link. Send an `Idempotency-Key` header to avoid duplicate links on retries.

Headers: `Authorization`, `Idempotency-Key` (string).

Body:

| Field | Type | Required | Notes |
|---|---|---|---|
| country_code | string | Yes | ISO 3166-1 alpha-2 or alpha-3, pattern `^[A-Za-z]{2,3}$` |
| name | string | Yes | |
| email | string (email) | Yes | |
| mobile | string | No | E.164 recommended, not enforced |
| amount | number (double) | Yes | |
| currency | string | No | |
| transaction_id | string | Yes | Client-generated; duplicates give 409 |
| description | string | No | |
| pass_digital_charge | boolean | Yes | |
| callback_url | string (uri) | No | Receives status webhooks; also the post-success redirect |

Responses:

- **200 / 201**: `{ data: { id: integer, payment_link: uri, transaction_id: string }, message: string, status: integer }`
- **400 / 422**: `{ status, message, validation }`
- **401**: auth failed or missing token
- **404**: country or currency not supported
- **409**: duplicate `transaction_id` or idempotency mismatch
- **429**: too many requests
- **500**: internal error
- Error shape for 401/404/409/429/500: `{ status: "error", errors: [{ code, message, field|null }] }`

- **Success:** if `callback_url` is set, redirect there; otherwise `https://app.swychrconnect.com/payment_success`.
- **Failure:** always `https://app.swychrconnect.com/payment_failed`.

## Webhooks

If `callback_url` was provided at link creation, the platform POSTs a `PaymentLinkStatusResponse` body to it on every status update. The merchant must respond **200** to acknowledge (400 for an invalid payload).

Headers sent with the callback (the spec's callback section lists these):

- `X-Webhook-Event`: `PaymentStatusUpdated` (required)
- `X-Webhook-Signature`: HMAC signature for verification
- `X-Webhook-ID`: unique ID for this delivery (use for deduplication)
- `X-Callback-URL`: the callback URL receiving this request (required)
- `Authorization`: listed in the spec; contents not described

### Webhook documentation (authoritative, from the vendor's "SwychrPay" webhook page)

#### Request headers

| Header | Description |
|---|---|
| X-Webhook-Timestamp | Unix epoch seconds at the moment of signing. Use it to reject stale or replayed requests |
| X-Webhook-Signature | HMAC-SHA256 **hex** digest of `{timestamp}.{raw_body}`, signed with your webhook secret |
| Content-Type | application/json |
| User-Agent | rails_webhook_system/1.0 |

#### Verifying the signature

Always verify before trusting a payload. Recompute HMAC-SHA256 over `` `${timestamp}.${rawBody}` `` with the webhook secret and compare to `X-Webhook-Signature` with a constant-time comparison. Reject timestamps more than a few minutes old (vendor example uses 300 seconds).

```js
const crypto = require('crypto');

function isValidSwychrWebhook(req, secret) {
  const timestamp = req.headers['x-webhook-timestamp'];
  const signature = req.headers['x-webhook-signature'];
  const rawBody = req.rawBody; // capture the raw, unparsed body

  // Reject requests older than 5 minutes to guard against replay
  const age = Math.abs(Date.now() / 1000 - Number(timestamp));
  if (!timestamp || age > 300) return false;

  const expected = crypto
    .createHmac('sha256', secret)
    .update(`${timestamp}.${rawBody}`)
    .digest('hex');

  return crypto.timingSafeEqual(
    Buffer.from(expected, 'utf8'),
    Buffer.from(signature || '', 'utf8')
  );
}
```

Caveat: `crypto.timingSafeEqual` throws if the two buffers differ in length, so check lengths first (or catch) when a bad signature is sent. The signature must be computed over the exact raw body bytes, so in Next.js read `await request.text()` before any JSON parsing.

#### Status reference

Value of `data.data.attributes.status`:

| Code | Meaning |
|---|---|
| 0 | PENDING |
| 1 | SUCCESSFUL |
| 2 | FAILED |
| 3 | EXPIRED |
| 4 | PROCESSING |
| 5 | DECLINED |
| 6 | REJECTED |

This replaces the earlier "suggested mapping" (3 = refunded was wrong). Only `1` means paid.

#### Retry policy

If the endpoint times out, refuses the connection, or returns non-2xx, delivery is retried up to **5 times with backoff**, then abandoned. The same event may arrive more than once, so the handler must be idempotent.

#### Best practices (vendor)

- Verify `X-Webhook-Signature` before reading the payload.
- Respond `200` immediately; process asynchronously.
- Deduplicate using `transaction_id` (retries can repeat an event).
- Reject requests with a stale `X-Webhook-Timestamp`.

| bank_code | string | No | e.g. `"011"`; presumably required for bank transfers |
| account_number | string | No | e.g. `"0123456789"`; presumably required for bank transfers |

200 (blank placeholders in the example):


Error responses are not documented for this endpoint. The "required if bank_transfer" notes on `bank_code` and `account_number` are my inference, not from the docs.

## POST /transaction_status

Body: `{ "transaction_id": "<id>" }` (required).

200:

```json
{
  "status": null,
  "message": "",
  "data": {
    "transaction_id": "",
    "status": "pending",
    "amount": null,
    "currency": "",
    "updated_at": "",
    "provider_reference": "",
    "failure_reason": ""
  }
}
```

`data.status` is a **string** enum here: `pending`, `processing`, `success`, `failed`, `refunded`, `cancelled`. Unlike payin, where `status` is an integer. `provider_reference` and `failure_reason` are nullable. Only `success` means the money was sent.

## PUSD endpoints

PUSD is not explained in the docs (presumably a stablecoin / platform balance unit; confirm with the vendor).

### POST /fiat_to_pusd_conversion

Body: `{ "currency_code": "<ISO currency>", "fiat_amount": <number> }` (both required). 200 response is only `{ "status": null, "message": "" }` in the example, so the result shape is unknown.

### POST /pusd_to_fiat_rate

Body: `{ "country_code": "<code>", "amount": <number> }` (both required). 200: `{ "status": null, "message": "", "data": {} }`, so the rate shape is unknown.

## Payout gaps / open questions

- No payout webhook is documented. Without one, poll `/transaction_status` until a final state (`success`, `failed`, `refunded`, `cancelled`).
- Payout transaction states `refunded` and `cancelled` are only in the status enum; how/when they occur is not explained.
- How the payout is funded (balance, PUSD, prefunding) and any fees/limits are not described.
- Error responses for `create_transaction`, `transaction_status`, and `payout_methods` are not shown.
- Which countries and methods exist besides Nigeria / `bank_transfer`.
- Whether `create_transaction` is idempotent on `transaction_id` and what a duplicate returns.
- Whether the payout token is interchangeable with the payin token or the `Api-Key`.
- IP whitelist: Part 1 says it applies to Direct API; assume it applies to payouts too.
